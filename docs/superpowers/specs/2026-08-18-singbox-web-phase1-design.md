# sing-box Web 管理页面一期设计

状态：本次范围调整已由用户批准，等待书面规格复核。

日期：2026-08-18

## 1. 背景

当前仓库是一个零依赖的 sing-box Web 控制台交互原型。它已经覆盖仪表盘、多个配置档案、官方配置顶层模块、入站、出站、DNS、路由、规则集、订阅和设置等界面，但核心状态、配置保存、订阅同步、规则下载和运行操作仍是浏览器内的演示行为。

一期以浏览器直接访问 Go HTTP 服务作为交付基线。完整产品未来需要负责 sing-box 的启动、停止、重启、状态、日志、连接、策略组和其他运行操作。本期只实现可靠的配置管理，并为后续核心控制留下稳定边界。

## 2. 一期目标

一期交付一个 Linux 单机部署的 Web 应用，满足以下目标：

- 通过应用内单管理员认证保护管理页面。
- 管理多套彼此独立的 sing-box 配置档案。
- 每套档案以完整配置对象为逻辑模型，以多个顶层模块 JSON 文件为正式磁盘产物。
- 自动保存服务器端草稿，显式执行校验和正式写入。
- 使用随 Web 发布且与稳定目标 sing-box 1.13.19 对应的固定官方 Schema、应用语义检查和本机 `sing-box check` 作为发布门槛。
- 以当前前端为视觉原型，保留完整导航，但明确禁用一期未接入的功能，不显示模拟运行数据。
- 以现有 `temp/config.default.json` 内容作为新档案的默认配置基准。
- 用仓库内的设计文档记录二期核心控制的接口边界和演进路线，使新上下文能够直接接续。

## 3. 明确非目标

一期不包含：

- 启动、停止、重启、重载或监督正在运行的 sing-box。
- 查询真实流量、内存、连接、日志、策略组、延迟或核心状态。
- 代理节点订阅 URL 的下载、解析、同步或定时刷新。
- Web 端规则资源中心的下载、编译或定时更新。配置中的原生远程 `route.rule_set` URL 仍可正常编辑和输出，生成配置后可由 sing-box 自身按原生行为下载；该下载不由 Web 发起或调度。
- TUN、系统代理、系统 DNS、防火墙或路由操作。
- 导入或接管服务器已有 sing-box 配置目录。
- 旧版 sing-box 兼容、字段迁移或多版本适配。
- 多管理员、角色和权限系统。
- 配置历史、版本浏览或回滚。
- SQLite 或其他数据库。
- Caddy 或其他反向代理配置、HTTPS/TLS、域名与证书管理、公网部署及其安全加固。
- 合并 `config.json` 下载、完整或脱敏配置复制及其他配置导出功能。
- 绕过校验强制写入无效配置。

一期允许调用本机 sing-box 的范围仅限版本查询和配置检查，不属于运行核心接入。

## 4. 已选技术方案

采用 Go 模块化单体和 Vue 3/TypeScript SPA：

- Go 提供认证、JSON 应用数据、配置档案、草稿、校验、文件发布和 API。
- Vue 3、TypeScript、Vite 负责复杂配置表单、JSON 编辑、多档案状态和响应式界面。
- 前端构建产物通过 `go:embed` 嵌入 Go 程序。
- Go 服务直接提供同源 HTTP 管理页面和 API。
- 生产环境只部署一个可执行文件和一个 systemd 服务。

未选择继续扩展原生单文件 JavaScript，因为现有 `src/app.js` 已同时承担数据、渲染、事件和业务规则，后续实时核心状态会进一步放大维护和测试成本。未选择服务端渲染方案，因为配置编辑包含大量动态表单、排序、引用关系、JSON 往返和未来实时数据。

## 5. 总体架构

```text
浏览器
    │ HTTP
    ▼
Go 单体服务
    ├── 内嵌 Vue SPA
    ├── Auth：管理员认证与会话
    ├── Profile：配置档案与草稿
    ├── Config：配置模型、表单映射、拆分与敏感字段保护
    ├── Validation：Schema、语义检查、sing-box check
    ├── Publication：多文件生成与原子发布
    ├── Capabilities：一期与后续能力声明
    └── CoreController：二期扩展边界，一期无实现
        │
        ├── JSON 应用数据目录
        └── 多套正式 sing-box 配置目录
```

配置管理和未来运行控制必须保持分离：

- Profile 模块只描述编辑、草稿和磁盘发布状态。
- CoreController 才能描述核心实际运行状态和实际使用的档案。
- “正在编辑”“已写入磁盘”“核心正在使用”是三个不同状态。
- 前端通过 capabilities 判断功能是否可用，不依赖伪造数据或写死的演示状态。

## 6. 应用数据存储

### 6.1 目录结构

应用内部数据目录与正式配置根目录必须分别配置。建议生产路径分别为 `/var/lib/singbox-web` 和 `/etc/sing-box/web-profiles`，部署者可以通过启动参数覆盖。

```text
data-dir/
├── auth.json
├── profiles.json
├── drafts/
│   └── <profile-id>.json
└── app.lock
```

- `auth.json`：Argon2id 密码哈希、会话签名密钥和会话失效代次。
- `profiles.json`：档案元数据、草稿修订号、已发布修订号、摘要和最近校验结果。
- `drafts/<profile-id>.json`：完整配置对象及 JSON 编辑器缓冲。
- `app.lock`：服务进程独占锁。

### 6.2 写入规则

- 所有应用 JSON 文件先写入同目录临时文件，再依次执行文件同步、原子重命名和目录同步。
- 进程启动时获取 `app.lock` 独占锁；无法获取时拒绝启动，禁止两个实例共享同一数据目录。
- `auth.json` 和草稿文件使用仅服务用户可读写的权限。
- `profiles.json` 或 `auth.json` 损坏时拒绝启动并报告路径，不自动重置。
- 单个草稿损坏时服务可以启动，但对应档案进入只读错误状态；不得用默认配置覆盖损坏文件。
- 应用数据不保存配置历史。

### 6.3 草稿结构

每个草稿包含：

- 当前递增 `revision`。
- 完整且最近一次有效的 sing-box 配置对象。
- 各模块原始 JSON 编辑器的文本缓冲。
- 缓冲是否已成功解析并应用到配置对象。
- 最近自动保存时间。

无效 JSON 文本以字符串形式保存，避免刷新页面丢失输入；在其恢复有效前，不替换完整配置对象并禁止发布。

## 7. 管理员认证与会话

### 7.1 初始化

应用只支持一个管理员。生产服务启动前，部署者执行交互式命令：

```text
singbox-web admin set-password --data-dir <目录>
```

管理员用户名固定为 `admin`，一期不提供用户名修改。密码只从终端交互读取，不通过命令参数、环境变量或日志传递。初始化命令同时生成会话签名密钥，后端只保存 Argon2id 哈希和随机签名密钥。未初始化管理员时，`serve` 拒绝启动 Web 服务并在本地给出操作指引。

### 7.2 会话安全

- 会话使用 HMAC 签名的 `HttpOnly`、`SameSite=Strict` Cookie；一期不设置 `Secure` 属性，以支持直接 HTTP 访问。后续传输层加固见 15.2 节。
- 默认在 24 小时无操作后过期，并在有效请求期间按节流策略续期。
- 修改密码时同时轮换会话签名密钥和失效代次，使所有既有会话立即失效。
- 退出登录清除浏览器 Cookie。
- 所有写请求必须同时通过 Cookie 和 CSRF Token 检查。
- 登录失败使用统一响应，并按来源和账号执行限速。
- API 不开放跨域访问。

## 8. 配置档案模型

### 8.1 标识

每套档案包含：

- `id`：服务端生成的随机内部 ID。
- `name`：可修改的用户显示名称。
- `slug`：创建时确定且之后不可修改的目录名。
- `draftRevision`：最新服务器草稿修订号。
- `publishedRevision`：最近成功发布的草稿修订号；未发布时为空。
- `publishedDigest`：最近正式配置的内容摘要。
- `publishedAt`：最近正式写入时间。
- `lastValidation`：最近检查状态和不含敏感数据的摘要。

`slug` 只允许小写字母、数字和连字符，必须匹配 `^[a-z0-9][a-z0-9-]{0,62}$`，并在配置根目录内唯一。所有路径由后端使用内部 ID 和 slug 构造；客户端不能提交绝对路径或路径片段。

### 8.2 新建档案

新档案不导入任何现有服务器配置。创建流程为：

1. 读取编译进可执行文件的默认配置资源，其内容基准来自仓库现有 `temp/config.default.json`。
2. 生成 32 个随机字节并编码为十六进制，替换 `experimental.clash_api.secret`。
3. 生成带 `ID_` 前缀的独立随机 `cache_id`。
4. 创建服务器端草稿和档案元数据。
5. 不创建正式配置目录，直至管理员首次执行“校验并写入”。

实施时必须将默认模板纳入受版本控制的嵌入资源，不能在生产运行时依赖 `temp` 目录。

### 8.3 唯一事实来源

完整 sing-box 配置对象是草稿的唯一语义事实来源：

- 结构化表单通过明确的 JSON 路径修改该对象。
- 常用字段提供结构化编辑。
- 每个顶层模块都提供完整 JSON 编辑兜底。
- 模块 JSON 保存成功后重新解析并刷新结构化表单。
- 结构化修改不得删除未识别字段。
- 最新版 Schema 中尚未结构化支持的字段必须可通过 JSON 编辑并无损往返。

## 9. 多文件正式配置

### 9.1 文件映射

每个存在的顶层模块写入一个文件；不存在的模块不生成空文件。

| 文件 | 顶层键 |
|---|---|
| `00-schema.json` | `$schema` |
| `10-log.json` | `log` |
| `20-dns.json` | `dns` |
| `30-ntp.json` | `ntp` |
| `40-certificate.json` | `certificate` |
| `41-certificate-providers.json` | `certificate_providers` |
| `42-http-clients.json` | `http_clients` |
| `43-network-namespaces.json` | `network_namespaces` |
| `50-endpoints.json` | `endpoints` |
| `60-inbounds.json` | `inbounds` |
| `70-outbounds.json` | `outbounds` |
| `80-route.json` | `route` |
| `90-services.json` | `services` |
| `99-experimental.json` | `experimental` |

每个文件必须是只包含相应顶层键的 JSON 对象。输出顺序和缩进必须确定，确保同一配置生成稳定内容摘要。

一期只发布上述模块文件，不生成或提供合并后的 `config.json` 下载、复制或导出接口。发布预览以将写入的模块文件为单位，模块目录中不得出现额外的合并配置，否则配置目录模式会重复合并相同内容。

### 9.2 正式目录入口

为了同时切换整套文件，每个 slug 是指向不可变发布目录的稳定符号链接：

```text
config-root/
├── profile-a -> .generations/<profile-id>/<publication-id>
└── .generations/
    └── <profile-id>/
        └── <publication-id>/
            ├── 10-log.json
            ├── 20-dns.json
            └── ...
```

外部 sing-box 或 systemd 使用稳定的 `config-root/profile-a` 作为 `-C` 目录。Web 一期不判断外部核心是否正在使用该目录。

`publication-id` 编码已发布草稿修订号和摘要前缀，使服务能够仅根据符号链接目标恢复发布状态。稳定符号链接是磁盘发布状态的最终事实来源。

旧发布目录保留到符号链接切换和 `profiles.json` 提交均完成后再删除。本结构只用于原子发布，不提供历史或回滚。进程若在事务中崩溃，下一次启动先根据稳定链接、publication ID 和实际摘要修复元数据，再清理未被任一档案入口引用的临时目录和遗留发布目录。恢复结果只可能是完整旧版本或完整新版本，不允许出现混合文件集。

### 9.3 文件权限

- 内部应用数据目录默认 `0700`，文件默认 `0600`。
- 正式配置目录默认 `0750`，配置文件默认 `0640`。
- 正式配置可以设置为 sing-box 服务所属的共享组，使核心具有只读权限。

## 10. 草稿自动保存与并发

前端使用防抖自动保存。读取草稿时服务通过 `ETag` 返回当前修订，写入草稿时客户端必须通过 `If-Match` 携带期望 `revision`：

1. 后端仅在期望修订等于当前修订时接受更新。
2. 成功后写入草稿并递增修订号。
3. 旧标签页提交过期修订时返回 `409 Conflict` 和最新修订号。
4. 前端保留未提交内容，提供重新载入服务器版本或明确覆盖的选择，禁止静默覆盖。
5. 浏览器断线时保留尚未确认的修改并显示离线状态；恢复后按最新修订重试。
6. 页面存在未确认修改时，关闭或刷新前给出提示。

“草稿已保存”只表示应用 JSON 已落盘，不表示正式配置已写入，也不表示核心已应用。

## 11. 校验与发布流程

### 11.1 校验层次

发布必须依次通过：

1. 所有 JSON 编辑器缓冲均可解析。
2. 随 Web 版本打包、固定到稳定目标 sing-box 1.13.19 的官方 JSON Schema。
3. 应用语义检查，包括 tag 唯一性、出站引用、DNS 引用、规则集引用、条件必填字段和模块间关系。
4. 本机 sing-box 配置目录检查。

Web 不进行旧版本转换。页面同时显示 Web 打包时的目标版本和本机 `sing-box version`；版本不一致时显示显著警告，但不尝试迁移字段，最终以本机 `sing-box check` 的实际结果决定能否发布。

官方 live Schema URL 可能领先稳定二进制：2026-08-19 时 `https://sing-box.sagernet.org/schema.json` 已提前到 1.14 字段，不能标记为 1.13.19。本期固定官方仓库 deployment commit `583a690e888cdf6e8b024bf017ebf6297e08338d` 的 `schema.json`（SHA-256 `ee03dcaffe9282100418de280c61d3f0c8022712af50bc79c072994247133c41`），并保留 1.13 的 `dns.independent_cache` 与 remote rule-set `download_detour`；更新资产时必须同时验证版本、commit、SHA 与这两个稳定字段。

### 11.2 发布事务

“校验并写入”执行以下步骤：

1. 要求客户端提交当前草稿修订号，并在事务期间锁定该档案发布操作。
2. 执行解析、Schema 和语义校验。
3. 在 `config-root/.generations/<profile-id>/` 内创建仅本次使用的临时发布目录。
4. 生成确定性的模块文件并设置权限。
5. 不经过 shell，直接执行：

   ```text
   sing-box check -C <临时发布目录>
   ```

6. 检查进程默认 30 秒超时，标准输出和标准错误分别限制为 64 KiB，并执行敏感信息清理。
7. 成功后将临时目录变为不可变发布目录，创建新符号链接并用原子重命名替换稳定 slug 入口。
8. 写入 `publishedRevision`、摘要、时间和校验结果。
9. 元数据提交成功后删除旧发布目录和临时资源。

符号链接切换前发生任何错误时，旧符号链接和旧正式配置保持不变。切换后元数据提交失败时，服务首先原子恢复旧链接；如果恢复也失败，则立即停止新的发布操作并进入受限状态，由启动恢复逻辑依据实际链接修复。进程崩溃后，客户端必须重新读取发布状态，不能仅依据中断请求的结果判断成功或失败。草稿始终保留。系统不提供忽略错误强制发布的入口。

### 11.3 外部修改检测

正式目录由 Web 管理。发布前重新计算当前正式目录摘要；如果与 `publishedDigest` 不一致，视为外部修改，阻止静默覆盖并要求管理员明确确认重新发布。确认操作只允许用当前有效草稿覆盖，仍不导入外部内容。

### 11.4 缺少 sing-box

找不到配置的 sing-box 二进制、无法执行、检查超时或退出码非零时：

- 登录、草稿编辑和 JSON 预检仍可使用。
- 正式发布能力禁用。
- 页面显示全局告警和经过清理的错误摘要。

## 12. 敏感字段保护

- 页面预览默认遮罩密码、Token、Secret、UUID、私钥和其他被字段目录标记为敏感的值。
- 配置正文和敏感值不得进入应用日志。
- 后端错误响应不得包含敏感字段值。

## 13. 前端信息架构

### 13.1 技术组织

Vue 前端按功能拆分：

- `auth`：登录、会话和密码修改。
- `profiles`：档案列表、创建、重命名、删除和切换。
- `config-editor`：模块表单、JSON 编辑、引用关系和错误定位。
- `publication`：草稿状态、检查、差异和写入。
- `capabilities`：一期和未来能力开关。
- `settings`：主题、界面偏好和管理员设置。
- `runtime`：二期 CoreApi 边界，一期只有不可用状态组件。

使用 TypeScript API 客户端和集中状态管理区分服务器已确认状态、前端未确认修改和运行能力。继续复用当前原型的视觉语言、响应式布局、深浅主题和主要导航结构，不复用其演示状态和单文件业务组织。

### 13.2 页面行为

- 登录页：仅用户名和密码，不提供注册或找回密码。
- 仪表盘：显示档案数量、草稿状态、最近校验结果、Web 目标版本和本机 sing-box 版本；运行指标显示二期尚未接入。
- 配置工作区：保留概览、DNS、入站、出站、端点、路由、服务和高级标签。
- 订阅页面：保留导航和说明，明确显示尚未接入，不展示模拟节点或同步状态。
- 规则集页面：Web 远程中心、下载和定时更新不可用；配置工作区中的 `route.rule_set` 编辑仍可用，发布后的 remote rule set 可由 sing-box 自身下载。
- 设置页：支持管理员密码、主题和界面偏好；核心自动启动、重载等设置显示为二期能力。
- 通知、测速、启停、重启、流量和连接操作在一期禁用并解释原因。

### 13.3 配置交互

- 原“保存并应用”改为“校验并写入”。
- 持续显示草稿保存中、已保存、冲突、与磁盘一致或有待发布修改。
- 发布前可查看将生成的模块文件和草稿相对当前磁盘内容的临时差异；发布后不保留历史差异。
- 校验错误汇总可跳转到模块和字段。
- 敏感字段默认遮罩，显式操作后才能临时显示。
- 多配置侧栏支持新建、修改显示名称、删除和切换；slug 只读，并可复制目录和检查命令。
- 删除档案必须输入显示名称确认，同时删除草稿和正式目录，且不可恢复。
- 删除时必须提示一期无法判断该目录是否正被外部核心使用。

## 14. HTTP API

API 使用同源 `/api/v1` 前缀：

- `POST /auth/login`：建立会话。
- `POST /auth/logout`：退出并清除 Cookie。
- `GET /auth/session`：获取当前会话。
- `PUT /auth/password`：修改密码并使全部会话失效。
- `GET /capabilities`：返回配置管理、发布、订阅和核心控制等能力状态。
- `GET /profiles`：列出档案和状态摘要。
- `POST /profiles`：从默认模板创建档案。
- `PATCH /profiles/{id}`：修改显示名称。
- `DELETE /profiles/{id}`：确认后删除档案。
- `GET /profiles/{id}/draft`：读取草稿。
- `PUT /profiles/{id}/draft`：使用 `If-Match` 携带期望修订并保存完整草稿包，成功响应返回新 `ETag`。
- `POST /profiles/{id}/validate`：执行解析、Schema 和语义检查，不修改正式目录。
- `POST /profiles/{id}/publish`：执行完整校验和原子发布。

错误响应包含稳定错误码、用户可读信息、字段路径和必要的最新修订号。不得直接暴露 Go 内部错误、服务器绝对路径、敏感配置或进程环境。

`/api/v1/core` 命名空间为二期保留，一期不提供返回假状态的处理器。

## 15. 应用与主机安全

### 15.1 一期范围

- Go 服务直接提供 HTTP，默认只监听 `127.0.0.1`。
- 静态资源和 API 同源，不配置宽松 CORS。
- 响应设置严格 CSP、`X-Content-Type-Options`、`Referrer-Policy` 和合适的缓存策略。
- API 设置总请求体和单模块 JSON 大小限制。
- 配置路径经过 slug 校验、根目录包含性检查和符号链接目标检查，防止目录穿越。
- Go 服务以专用非 root 用户运行。
- systemd 使用 `NoNewPrivileges`、`PrivateTmp`、只读系统目录和精确 `ReadWritePaths`；仅允许写应用数据目录和正式配置根目录。
- sing-box 检查进程直接继承受限服务身份，不通过 shell，也不提升权限。

### 15.2 后续部署与维护

后续维护人员如需 HTTPS 或公网访问，可以按实际环境在 Go 服务前增加 Caddy 或其他反向代理。例如：

```text
浏览器
    │ HTTPS
    ▼
Caddy 或其他反向代理
    │ HTTP
    ▼
Go 服务
```

该拓扑仅用于说明可能的演进方向，不构成一期实现契约。域名、证书、TLS 配置、HSTS、转发头信任策略、`Secure` Cookie、公网访问控制和安全审查均由后续维护人员负责；一期不提供或验证反向代理配置，也不以这些内容作为测试或验收条件。

## 16. 异常处理

| 异常 | 行为 |
|---|---|
| 表单或 JSON 无效 | 保存文本缓冲，保留最近有效对象，禁止发布 |
| 草稿修订冲突 | 返回 `409`，保留双方内容，不自动覆盖 |
| Schema 或引用错误 | 返回模块和字段路径，正式配置不变 |
| `sing-box check` 失败或超时 | 保留草稿和旧正式目录，清理临时目录 |
| 二进制不存在 | 编辑可用，发布禁用并显示全局告警 |
| 文件写入或链接切换失败 | 旧入口继续有效，报告准确失败阶段 |
| 浏览器断线 | 保留未确认修改，恢复后按修订号重试 |
| 核心应用 JSON 损坏 | 不自动重置；按文件重要性拒绝启动或隔离档案 |
| 正式目录外部漂移 | 阻止静默覆盖，要求明确确认重新发布 |

运行日志只记录操作类型、档案内部 ID、修订号、内容摘要、耗时和结果。`sing-box check` 输出先限制长度再清理敏感信息。

## 17. 测试策略

### 17.1 Go 单元测试

- JSON 原子写入、文件锁和损坏处理。
- slug 校验、目录穿越和符号链接边界。
- 配置拆分、模块重组校验、稳定序列化和摘要。
- 未知字段往返。
- tag、出站、DNS 和规则集引用检查。
- 草稿修订冲突、认证、CSRF 和登录限速。

### 17.2 Vue 单元与组件测试

- 结构化字段正确修改 JSON 路径。
- JSON 编辑与表单往返一致。
- 草稿保存、冲突、离线和校验错误状态。
- 敏感字段遮罩和显式临时显示。
- 未接入页面不显示模拟数据或可执行按钮。

### 17.3 后端集成测试

- 使用临时应用目录和正式配置根目录。
- 使用可控的假 sing-box 可执行程序模拟成功、失败、超时和异常输出。
- 验证失败发布不会改变稳定链接。
- 验证成功发布只包含预期顶层模块文件。
- 在符号链接切换和元数据提交的各个故障点模拟进程中断，验证启动恢复后只得到完整旧版本或完整新版本。
- 验证服务重启后档案和草稿恢复。

### 17.4 最新 sing-box 契约测试

- 测试元数据记录真实二进制完整版本和对应官方 Schema。
- 代表性完整配置必须通过 Schema 和 `sing-box check -C`。
- 自动化只允许调用 `sing-box version` 和 `sing-box check`，不得调用 `run` 或改变网络状态。
- 测试环境不使用真实节点密码、订阅凭据、证书私钥或生产配置。

### 17.5 浏览器端到端测试

- 初始化管理员、登录、退出和修改密码。
- 创建档案、自动保存、刷新恢复和多标签冲突。
- JSON 编辑、字段错误跳转、校验和发布。
- 直接 HTTP 访问下的 Cookie、CSRF、安全响应头和 SPA 路由。

## 18. 一期验收标准

一期只有同时满足以下条件才完成：

- 单个 Go 可执行文件可以在 systemd 下运行并直接提供 HTTP 管理页面和 API。
- 没有管理员凭据或目录权限不安全时拒绝启动。
- 新档案与默认模板语义一致，但 Secret 和 `cache_id` 对每个档案唯一。
- 多文件正式目录完整表达草稿中的配置对象，且不生成额外的合并 `config.json`。
- 常用字段可结构化编辑，最新版未知字段可通过 JSON 编辑并无损保留。
- 草稿在浏览器刷新和服务重启后恢复。
- 并发旧修订不会静默覆盖新修订。
- 任何校验或文件错误都不会破坏已发布配置。
- 未通过真实 `sing-box check` 的配置不能正式发布。
- 敏感值不会进入普通预览或日志。
- 页面和 API 不提供合并 `config.json` 下载、完整或脱敏配置复制及其他配置导出功能。
- 运行控制和订阅同步明确不可用，不存在伪造结果。
- Go、Vue、集成、真实二进制契约和端到端测试全部通过。

## 19. 二期接口边界

一期必须留下以下稳定契约：

- 档案具有稳定 ID、稳定目录入口、草稿修订、发布修订和发布摘要。
- 正在编辑的档案不等于核心正在使用的档案。
- 前端运行页面只依赖独立 CoreApi 和 capabilities。
- Clash API Secret 只由后端读取，未来也不直接暴露给浏览器。
- 配置发布服务不调用核心启动、停止或重载。

二期 CoreController 负责：

- 发现 sing-box 版本、进程和运行状态。
- 使用某个已发布档案启动、停止、重启或重载核心。
- 报告核心实际使用的档案 ID、发布修订和启动时间。
- 串行化运行操作并实现超时、幂等和状态机，避免重复启动或并发重启。
- 连接 Clash API，提供模式、策略组、节点、连接、流量、内存和日志。
- 向前端提供实时事件流，并支持断线后的完整状态重同步。
- 每次启动或重启前重新校验配置；失败不得破坏已有运行实例。

## 20. 演进路线与交接

后续按独立规格拆分：

1. 二期 A：只读接入核心发现、版本、状态、日志和实时指标。
2. 二期 B：选择已发布档案并实现启动、停止、重启和异常恢复。
3. 二期 C：模式、策略组、测速、连接管理和实时日志控制。
4. 后续独立阶段：订阅拉取、规则资源调度、TUN、系统代理和系统 DNS。

二期仍不得让 Web 主进程以 root 运行。systemd 控制或受限辅助进程的具体权限模型必须在二期设计中单独确定；一期文件写权限不能顺带扩展为系统网络权限。
