## 1. 背景

当前仓库是一个零依赖的 sing-box Web 控制台交互原型。它已经覆盖仪表盘、多个配置档案、官方配置顶层模块、入站、出站、DNS、路由和设置等界面，但配置保存、规则资源、核心进程和运行操作仍是浏览器内的演示行为。

一期把它实现为 Linux 单机上的本地管理应用。Web 保存独立配置，负责下载规则文件、生成并保留 sing-box 候选配置、执行真实检查、应用通过检查的配置，以及下载和更新 sing-box 程序。

Web 程序本身如何安装、启动、守护或接入 systemd 不属于本设计，由后续运维人员决定。Caddy、HTTPS、域名和公网部署同样不属于一期实现、测试或验收范围。

## 2. 一期目标

一期满足以下目标：

- 通过应用内单用户密码认证保护管理页面，不设置用户名。
- 管理多套彼此独立的配置档案，并自动保存服务器端草稿。
- 支持用户在出站模块 JSON 编辑器中手工粘贴或编辑代理节点，并无损保存和应用节点字段。
- 将 Web 应用配置与最终生成的 sing-box 配置文件明确分离。
- 多套档案只保留各自的 Web 草稿；sing-box 始终使用唯一的 `config` 目录，应用档案时整体替换该目录。
- 由 Web 管理远程规则资源的 URL、格式、更新周期和本地文件，支持立即下载与服务端定时更新。
- 不支持原生远程 `route.rule_set` 透传；远程来源由 Web 独立管理，正式 sing-box 配置只引用 Web 已下载的本地文件。
- 规则文件使用固定本地路径，不保存版本历史；下载成功后提示相关档案需要重新应用。
- 每个档案使用 `config.staging-<profile-id>` 保留最新完整检查候选；应用时复制已验证候选，不移动或删除该检查目录。
- 由 Web 直接管理一个 sing-box 子进程，报告运行状态、PID、当前档案、版本和启动错误。
- sing-box 不存在时允许管理员在页面手动下载；有新版时由管理员手动确认更新，禁止无人值守自动升级。
- 不维护固定 JSON Schema；以 Web 的基础语义检查和当前受管 sing-box 二进制的 `sing-box check` 作为应用门槛。
- 以当前前端为视觉原型，保留一期功能和后续运行控制需要的导航，删除没有产品规划的入口，不显示模拟运行数据。
- 以现有 `temp/config.default.json` 为默认内容基准，并在构建时转换成独立的档案模板与规则资源模板。
- 用本文件记录二期运行数据接入的稳定边界，使新上下文能够直接接续。

## 3. 明确非目标

一期不包含：

- Web 程序自身的安装、启动、守护、systemd 单元或主机开机启动方案。
- Caddy 或其他反向代理配置、HTTPS/TLS、域名与证书管理、公网部署及其安全加固。
- 多管理员、角色和权限系统。
- 不提供基于 URL 的代理节点拉取、解析、同步或定时刷新；“订阅配置”只管理不访问网络的本地 JSON 出站节点集合。
- 规则文件版本浏览、历史、回滚或编译；每个规则资源只维护一个固定的当前文件。
- sing-box 自动更新、预发布版本、任意历史版本选择或多版本兼容迁移。
- 独立的配置历史、版本浏览或用户可见回滚。
- SQLite 或其他数据库。
- 合并 `config.json` 下载、完整或脱敏配置复制及其他配置导出功能。
- 导入或接管服务器已有 sing-box 配置目录。
- 查询真实流量、内存、连接、策略组、延迟和完整核心日志，以及模式切换、连接管理等高级运行操作。
- TUN、系统代理、系统 DNS、防火墙或主机路由操作。
- 绕过检查强制应用无效配置。

一期开放配置应用和程序更新所需的核心控制；独立高级核心控制仍不开放。

## 4. 已选技术方案

采用 Go 模块化单体和 Vue 3/TypeScript SPA：

- Go 提供认证、JSON 应用数据、配置档案、规则资源下载与调度、配置生成、实际二进制检查、子进程管理、sing-box 更新和 API。
- Vue 3、TypeScript、Vite 负责表单、JSON 编辑、多档案状态、规则资源、核心状态和响应式界面。
- 前端构建产物通过 `go:embed` 嵌入 Go 程序。
- Go 服务直接提供同源 HTTP 管理页面和 API。
- Web 的安装和进程守护方式不进入应用架构契约。

未选择继续扩展原生单文件 JavaScript，因为现有 `src/app.js` 已同时承担数据、渲染、事件和业务规则。未选择服务端渲染，因为配置编辑包含大量动态表单、排序、引用关系和 JSON 往返。

不使用固定官方 JSON Schema。结构化表单由 Web 自身约束，原始 JSON 先做语法和应用引用检查，最终兼容性由当前实际安装的 sing-box 执行 `check` 决定，从而避免 Schema 与可执行程序版本漂移。

## 5. 总体架构

```text
浏览器
    │ HTTP
    ▼
Go 单体服务
    ├── 内嵌 Vue SPA
    ├── Auth：单用户密码认证与会话
    ├── Profile：档案、草稿与应用状态
    ├── RuleResource：规则来源、下载、定时更新与本地文件
    ├── ConfigGenerator：Web 模型到 sing-box 多文件配置
    ├── Validation：JSON、引用关系与 sing-box check
    ├── CoreManager：子进程启动、停止、状态与日志
    ├── CoreUpdater：官方版本检查、下载、校验与手动更新
    └── Capabilities：一期与后续运行能力声明
        │
        ├── 相对 JSON 应用数据目录
        ├── 相对固定规则文件目录
        ├── 相对受管 sing-box 可执行文件
        ├── 相对唯一正式配置目录
        └── sing-box 子进程
```

核心状态必须明确区分：

- “草稿已保存”：Web 应用模型已经落盘。
- “需要应用”：草稿或所引用的规则文件已变化，但 sing-box 尚未通过“应用”流程重新启动。
- “已应用”：指定草稿修订和规则文件摘要已生成正式配置，并成功启动 sing-box。
- “正在运行”：Web 当前管理的 sing-box 子进程仍存活。
- “当前档案”：该子进程启动时使用的档案。

一期只管理一个 sing-box 子进程。同一时刻只能有一个当前档案；应用另一档案会停止现有子进程并切换到新档案。

## 6. 应用数据与文件

### 6.1 目录结构

所有目录均使用相对于 Web 工作目录的固定路径，不接受绝对目录。应用数据目录固定为 `data`，sing-box 唯一正式配置目录固定为 `config`；程序不提供命令行参数、环境变量、应用配置、页面或 API 来修改这些目录。进程启动后工作目录保持不变；实际落盘位置只随运维设置的 Web 工作目录变化。

```text
work-dir/
├── data/
│   ├── auth.json
│   ├── profiles.json
│   ├── core.json
│   ├── rule-resources.json
│   ├── drafts/
│   │   └── <profile-id>.json
│   ├── rulesets/
│   │   └── <resource-id>.<json|srs>
│   ├── bin/
│   │   ├── sing-box
│   │   └── sing-box.bak
│   ├── logs/
│   │   └── sing-box.log
│   └── app.lock
└── config/
    ├── 10-log.json
    ├── 20-dns.json
    └── ...
```

- `auth.json`：Argon2id 密码哈希、会话签名密钥和会话失效代次。
- `profiles.json`：档案元数据、草稿修订、已应用修订、摘要和检查结果。
- `core.json`：已安装 sing-box 版本与摘要、当前档案、期望运行状态和最近启动错误。
- `rule-resources.json`：独立规则资源配置、调度状态、最近下载结果和内容摘要。
- `drafts/<profile-id>.json`：档案配置对象、规则资源绑定和 JSON 编辑器缓冲。
- `rulesets/<resource-id>.*`：该资源唯一的当前文件，不建立版本目录。
- `bin/sing-box.bak`：仅供一次程序更新失败时立即恢复，不构成多版本管理。
- `app.lock`：Web 进程独占锁。
- `config/`：当前已应用档案生成的唯一正式配置；其他档案只保留 Web 草稿，不拥有独立正式目录。

### 6.2 写入规则

- 应用 JSON、规则文件和程序下载先写同一文件系统中的临时文件，完成检查后原子重命名。
- 规则下载或格式检查失败时不得替换现有规则文件；成功替换后不保留旧规则版本。
- 所有应用 JSON 文件执行文件同步、原子重命名和目录同步。
- Web 启动时获取 `app.lock`；无法获取时拒绝运行，禁止两个实例共享同一数据目录或管理同一个子进程。
- `profiles.json`、`core.json`、`rule-resources.json` 或 `auth.json` 损坏时拒绝进入可写状态并报告文件。
- 单个草稿损坏时隔离对应档案，不得用默认值覆盖。
- Web 应用数据不保存配置历史。

## 7. 单用户密码认证与会话

### 7.1 初始化

应用只支持一个用户身份，只使用密码认证，不存在用户名或账号字段。首次使用前执行：

```text
singbox-web admin set-password
```

该命令固定读写 `data/auth.json`，不接受目录或文件参数。密码只从终端交互读取，不通过命令参数、环境变量或日志传递。初始化命令同时生成会话签名密钥；后端只保存 Argon2id 密码哈希和随机签名密钥，不保存用户名。未设置密码时，`serve` 拒绝提供管理页面并给出操作指引。

上述命令如何由运维执行、Web 进程如何被拉起，不属于本设计。

### 7.2 会话安全

- 会话使用 HMAC 签名的 `HttpOnly`、`SameSite=Strict` Cookie；一期不设置 `Secure`，以支持直接 HTTP 访问。
- 默认在 24 小时无操作后过期，并在有效请求期间按节流策略续期。
- 修改密码时轮换会话签名密钥和失效代次，使全部既有会话立即失效。
- 退出登录清除浏览器 Cookie。
- 所有写请求必须同时通过 Cookie 和 CSRF Token 检查。
- 登录失败使用统一响应，并按请求来源限速。
- API 不开放跨域访问。

## 8. 配置档案与 Web 模型

### 8.1 档案标识

每套档案包含：

- `id`：服务端生成的随机内部 ID。
- `name`：用户显示名称。
- `draftRevision`：最新服务器草稿修订，仅用于并发控制。
- `appliedRevision`：最近成功应用的草稿修订；未应用时为空。
- `appliedDigest`：最近生成配置和规则绑定的综合摘要。
- `appliedAt`：最近成功启动时间。
- `needsApply`：草稿或规则资源是否晚于最近成功应用。
- `lastValidation`：最近检查状态和错误摘要。

修订号不是用户可浏览的配置版本，也不提供历史和回滚。

正式配置目录固定为 `config`，档案没有目录名或路径字段。草稿文件和规则文件路径只由后端根据内部 ID 和规则资源 ID 构造；客户端不能提交绝对路径、路径片段或任何配置目录。

### 8.2 新建档案与默认模板

构建时从 `temp/config.default.json` 生成两类受版本控制的嵌入资源：

1. 档案默认模板：保留普通 sing-box 配置。
2. 规则资源默认模板：提取现有远程 `route.rule_set` 的 tag、format、URL 和更新周期。

当前默认配置中的远程规则集不原样透传：

- 每项远程规则集转换成全局 Web 规则资源。
- 档案保存对资源 ID 和 tag 的绑定。
- `download_detour` 不用于 Web 下载，也不进入最终本地规则集配置。
- 构建时从默认档案中移除原生远程条目；生成正式配置时再注入本地文件引用。
- 默认路由规则仍按原 tag 引用规则集。

新建档案时：

1. 由后端生成唯一的内部 ID。
2. 读取嵌入的档案模板和默认规则资源绑定。
3. 生成 32 个随机字节并编码为十六进制，替换 `experimental.clash_api.secret`。
4. 生成带 `ID_` 前缀的独立随机 `cache_id`。
5. 创建服务器端草稿和档案元数据。
6. 首次点击“应用”前不创建正式配置目录。

生产运行时不能依赖 `temp` 目录。

### 8.3 唯一事实来源

档案草稿包是 Web 配置的唯一事实来源，包含：

- 完整的常规 sing-box 配置对象。
- 各顶层模块的原始 JSON 编辑器缓冲。
- 规则资源绑定：`resourceId`、sing-box tag 和启用状态。
- 当前递增 `revision` 与最近自动保存时间。

规则资源的 URL、更新周期和固定本地文件属于 `rule-resources.json`，不属于 sing-box 配置对象。

结构化表单通过明确 JSON 路径修改配置对象；模块 JSON 保存成功后重新解析并刷新表单。结构化修改不得删除未识别字段。尚未结构化支持的合法字段必须可通过 JSON 编辑并无损往返。

手工本地或 inline `route.rule_set` 可以保留在配置对象中。原生 `type: "remote"` 不允许直接应用，用户必须先建立 Web 规则资源并绑定到档案。

## 9. 规则资源

### 9.1 模型

每个规则资源包含：

- `id`：随机稳定 ID，同时决定安全的本地文件名。
- `name`：显示名称。
- `url`：仅允许 HTTP 或 HTTPS。
- `format`：`source` 或 `binary`。
- `updateInterval`：服务端调度周期；为空表示只手动更新。
- `disabled`：是否暂停调度。
- `localPath`：由后端根据 ID 和格式生成，客户端只读。
- `lastAttemptAt`、`lastSuccessAt`、`lastDigest` 和 `lastError`。
- `nextUpdateAt`：下一次服务端计划更新时间。

删除仍被任一档案引用的资源时必须拒绝，并列出引用档案。

### 9.2 下载与定时更新

规则更新由 Go 服务执行，不依赖浏览器保持打开：

1. 对同一资源加锁，禁止手动更新和定时更新并发。
2. 使用受限 HTTP 客户端下载到临时文件。
3. 限制协议、重定向次数、连接与总超时、响应大小；每次重定向重新检查 URL。
4. `source` 格式必须是可解析的规则集 JSON；`binary` 至少检查非空和大小限制。
5. 格式检查成功后原子替换固定的 `rulesets/<resource-id>.*` 文件，不保留旧版本。
6. 内容摘要未变化时只更新时间，不设置 `needsApply`。
7. 内容发生变化时，把所有引用档案标记为 `needsApply=true`。

定时更新失败时保留现有文件，记录准确错误和下一次计划时间。没有成功下载文件的新资源会阻止相关档案应用。

Web 直接访问 URL，不解释也不使用 sing-box 的 `download_detour`。

### 9.3 生效提示

规则文件更新后，页面显示：

> 规则资源已更新，请点击“应用”使 sing-box 使用新规则。

不使用 PID 或进程启动时间推断规则是否生效。只有相关档案完整执行“应用”并成功启动后，才清除其 `needsApply` 状态。

## 10. sing-box 正式配置

### 10.1 文件映射

每个存在的顶层模块写入一个文件；不存在的模块不生成空文件。

| 文件 | 顶层键 |
|---|---|
| `10-log.json` | `log` |
| `20-dns.json` | `dns` |
| `30-ntp.json` | `ntp` |
| `40-certificate.json` | `certificate` |
| `41-certificate-providers.json` | `certificate_providers` |
| `42-http-clients.json` | `http_clients` |
| `43-network-namespaces.json` | `network_namespaces` |
| `60-inbounds.json` | `inbounds` |
| `70-outbounds.json` | `outbounds` |
| `80-route.json` | `route` |
| `90-services.json` | `services` |
| `99-experimental.json` | `experimental` |

每个文件只包含相应顶层键。输出顺序和缩进必须确定，以生成稳定摘要。

生成 `80-route.json` 时，ConfigGenerator 将规则资源绑定转换成 sing-box 本地规则集：

```json
{
  "type": "local",
  "tag": "geosite-cn",
  "format": "binary",
  "path": "data/rulesets/<resource-id>.srs"
}
```

最终配置不包含该资源的 URL、`download_detour` 或 `update_interval`。一期不生成或提供合并配置下载、复制或导出接口；预览以最终模块文件为单位。

### 10.2 按档案保留的检查目录

每个档案使用自身 ID 对应的持久检查目录，检查不会写入或替换正式 `config`：

```text
work-dir/
├── config.staging-<profile-id-a>/
│   ├── 10-log.json
│   ├── 20-dns.json
│   └── ...
└── config.staging-<profile-id-b>/
```

`config.staging-<profile-id>` 在检查成功或失败后都保留。再次检查同一档案时原子更新为最新完整候选；Web 启动恢复不得把它识别为事务残留或自动删除。检查目录不是已应用状态，也不会被 sing-box 运行进程自动采用。

## 11. 草稿自动保存与并发

前端使用防抖自动保存。读取草稿时服务通过 `ETag` 返回当前修订，写入时客户端必须通过 `If-Match` 携带期望修订：

1. 期望修订必须等于服务器当前修订。
2. 成功后写入草稿并递增修订号。
3. 旧标签页提交过期修订时返回 `409 Conflict` 和最新修订号。
4. 前端保留未提交内容，允许重新载入服务器版本或明确覆盖，禁止静默覆盖。
5. 浏览器断线时保留尚未确认的修改；恢复后按最新修订重试。
6. 页面存在未确认修改时，关闭或刷新前提示。

“草稿已保存”不表示配置已经生成，也不表示 sing-box 已重新启动。

## 12. 检查与应用

### 12.1 检查层次

检查依次执行：

1. 所有 JSON 编辑器缓冲均可解析。
2. Web 应用语义检查，包括 tag 唯一性、出站引用、DNS 引用、规则集引用、资源绑定、条件必填字段和模块关系。
3. 所有启用的规则资源具有成功下载的当前文件。
4. 生成并更新完整的档案检查目录。
5. 使用当前受管二进制直接执行：

   ```text
   data/bin/sing-box check -C config.staging-<profile-id>
   ```

不维护或下载 JSON Schema，不做字段迁移或多版本转换。检查命令及页面诊断中的程序和送检目录均使用相对 Web 工作目录的路径，不暴露主机绝对路径；页面展示实际安装版本、`sing-box check` 的错误、退出码、实际送检目录和文件名。当前二进制的检查结果是配置兼容性的最终依据。

检查默认 30 秒超时，标准输出和标准错误分别限制为 64 KiB；执行不经过 shell，输出会移除 Web 工作目录的绝对前缀，除此之外不改写核心诊断内容。

### 12.2 应用流程

“应用”先执行 12.1 所述完整检查。检查失败直接返回同一结构的诊断结果，不停止核心、不修改正式 `config`。检查成功后复制已验证输出，停止当前核心，原子替换唯一正式 `config`，启动所选档案并提交应用修订；切换、启动或状态提交失败时恢复此前目录和运行状态。固定检查目录始终保留。正式目录存在外部漂移时返回 `409`，只有用户确认现场摘要后才允许覆盖。

### 12.3 检查失败

- JSON 生成失败时保留此前完整的 `config.staging-<profile-id>`。
- 新候选完整生成后替换档案检查目录，再执行真实核心检查；检查失败仍保留本次候选以供后台审核。
- 检查不停止或启动核心，不写正式 `config`，也不改变已运行核心的状态。

## 13. sing-box 核心管理

### 13.1 子进程生命周期

CoreManager 直接持有 sing-box 子进程，不调用 systemd：

- 只允许一个受管子进程。
- 子进程使用相对程序路径、与 Web 相同的固定工作目录和参数数组，不经过 shell。
- 启动后记录 PID、版本、档案 ID、草稿修订、启动时间和状态。
- 捕获标准输出与标准错误到受限日志文件，限制单条消息和日志总大小。
- 停止时先发送优雅退出信号，默认等待 10 秒；超时后强制终止整个受管进程组。
- 子进程意外退出时记录退出码和最后错误，状态变为“启动失败”或“已停止”，一期不无限自动重启。
- Linux 下确保 Web 异常退出后受管子进程不会成为失去管理的孤儿。
- Web 正常启动后，如果 `core.json` 记录此前期望运行且存在已应用档案，则尝试重新创建子进程。
- Web 正常关闭时优雅停止子进程。

Web 如何被主机启动不影响上述内部生命周期，也不属于本设计。

### 13.2 缺少核心

没有可执行文件时：

- 登录、档案编辑、草稿保存、规则资源管理和规则下载仍可使用。
- “应用”禁用，并提示先下载 sing-box。
- 核心页面显示未安装状态和手动下载入口。

### 13.3 手动下载与更新

一期只检查官方最新稳定版，不自动更新，也不提供 alpha 或任意历史版本选择。

管理员点击“下载”或“更新”并确认后：

1. 从官方 Release 元数据解析当前 Linux 架构对应的资产。
2. 下载压缩包和官方 SHA-256 摘要到临时目录。
3. 校验摘要、压缩包路径安全和目标文件名。
4. 解压后设置执行权限，执行 `sing-box version`，确认架构可运行并记录真实版本。
5. 若存在已应用的 `config`，使用新二进制执行 `sing-box check -C config`；失败时不替换程序。
6. 获取全局核心操作锁；若核心正在运行，先优雅停止。
7. 将现有程序移动为唯一的 `sing-box.bak`，再原子安装新程序。
8. 使用固定 `config` 重新启动并观察启动结果，同时保留当前档案关联。
9. 成功后记录版本和摘要；失败则恢复 `.bak` 并尝试用旧程序重启。

首次下载没有旧程序时不生成 `.bak`。每次新更新会覆盖上一次备份，不形成版本列表。更新状态包含检查、下载、校验、安装、重启、完成或失败，页面可以轮询或接收事件。

## 14. 字段显示

一期不识别、遮罩或脱敏配置字段。配置编辑器、模块预览、检查错误和 sing-box 子进程输出直接显示原始值；错误和进程输出只做通用长度限制。

## 15. 前端信息架构

### 15.1 技术组织

Vue 前端按功能拆分：

- `auth`：登录、会话和密码修改。
- `profiles`：档案列表、创建、重命名、删除和切换。
- `config-editor`：模块表单、JSON 编辑、引用关系和错误定位。
- `rule-resources`：URL、格式、调度、本地文件、手动更新和状态。
- `application`：草稿状态、最终预览、检查、应用和恢复结果。
- `core`：安装版本、最新版本、进程状态、当前档案和手动更新。
- `capabilities`：一期和后续运行能力开关。
- `settings`：主题、界面偏好和密码设置。
- `runtime`：二期 Clash API 数据边界，一期只显示不可用能力。

### 15.2 页面行为

- 登录页：只显示密码输入框，不显示或接受用户名，不提供注册或找回密码。
- 仪表盘：显示档案数量、草稿与应用状态、规则更新时间、核心安装版本、运行状态、当前档案和最近错误。
- 配置工作区：依次保留配置概览、入站、出站、路由、DNS、服务和高级标签。
- 代理节点不设独立页面；用户在出站模块 JSON 编辑器中手工粘贴或编辑节点 JSON。
- 规则资源页面：创建、编辑、禁用、删除、立即更新和查看下一次更新时间；显示引用档案和最近错误。
- 核心页面或设置区：显示已安装版本和官方最新稳定版，提供需二次确认的下载/更新操作。
- 运行流量、连接、策略组、测速和完整日志明确显示二期尚未接入，不展示模拟数据。

### 15.3 配置交互

- “应用”按钮仅在草稿已保存、编辑无错误、核心已安装且无其他核心操作时可用；处理期间禁止重复提交。
- 持续显示草稿保存中、已保存、冲突和最近检查状态。
- 规则更新后，所有引用档案显示“规则已更新，请应用”。
- 预览显示最终生成的模块文件，包括规则资源被转换后的本地 `route.rule_set`。
- 检查结果显示固定候选目录、命令、文件、修订、摘要和核心输出。
- 检查错误可以跳转到模块；无法解析字段路径时直接显示 sing-box 原始错误。
- 多档案侧栏支持新建、改名、删除和切换；新建和改名只填写显示名称，不提供配置目录输入。
- 删除档案必须输入显示名称确认。删除非当前档案只删除其 Web 草稿；删除当前运行档案必须明确停止核心，并删除该草稿及固定 `config` 目录，或者先应用其他档案。

## 16. HTTP API

API 使用同源 `/api/v1` 前缀：

- `POST /auth/login`：请求体只接受密码，验证成功后建立会话；提交用户名或其他账号字段返回 `400`。
- `POST /auth/logout`：退出并清除 Cookie。
- `GET /auth/session`：只返回当前会话是否有效及过期信息，不返回用户名。
- `PUT /auth/password`：修改密码并使全部会话失效。
- `GET /capabilities`：返回配置、规则资源、应用、核心更新和后续运行能力状态。
- `GET /profiles`：列出档案和状态。
- `POST /profiles`：只接受显示名称，由后端生成 ID，再从默认 Web 模板创建档案；不接受配置目录或路径字段。
- `PATCH /profiles/{id}`：只接受显示名称；不接受配置目录或路径字段。
- `DELETE /profiles/{id}`：确认后删除档案；当前档案必须先切换，或明确停止核心并删除固定 `config`。
- `GET /profiles/{id}/draft`：读取草稿包。
- `PUT /profiles/{id}/draft`：使用 `If-Match` 保存草稿，成功响应返回新 `ETag`。
- `POST /profiles/{id}/validate`：更新并保留 `config.staging-<profile-id>`，使用当前二进制执行完整检查，不停止核心、不写正式目录。
- `POST /profiles/{id}/apply`：先检查指定草稿修订；成功后停止核心、复制并切换正式配置、启动和提交状态，失败返回检查结果或准确事务错误。
- `GET /rule-resources`：列出规则资源和调度状态。
- `POST /rule-resources`：创建资源。
- `PATCH /rule-resources/{id}`：修改来源、格式、周期或启用状态。
- `DELETE /rule-resources/{id}`：删除未被引用的资源。
- `POST /rule-resources/{id}/update`：立即下载并更新固定本地文件。
- `GET /core`：返回安装版本、运行状态、PID、当前档案和最近错误。
- `GET /core/releases/latest`：检查官方最新稳定版。
- `POST /core/update`：管理员确认后下载或更新 sing-box，并返回可跟踪的操作状态。
- `GET /core/update`：读取当前或最近一次更新状态。

错误响应包含稳定错误码、用户可读信息、阶段、字段路径和必要的最新修订号；字段值按原始内容显示。

配置检查和核心更新由全局操作锁串行化。规则资源更新使用资源级锁，并在检查快照期间保持内容稳定。

## 17. 应用、主机与部署安全

### 17.1 一期应用安全

- Go 服务直接提供 HTTP，默认只监听 `127.0.0.1`。
- 静态资源和 API 同源，不配置宽松 CORS。
- 响应设置严格 CSP、`X-Content-Type-Options`、`Referrer-Policy` 和合适缓存策略。
- API 设置总请求体和单模块 JSON 大小限制。
- 规则下载只允许 HTTP/HTTPS，限制响应大小、超时和重定向，并安全派生本地路径。
- sing-box 程序只从官方 Release 下载，必须通过官方 SHA-256 校验。
- 压缩包解压必须防止绝对路径、`..`、符号链接和其他目录穿越。
- 应用数据、配置、规则和程序使用 Web 工作目录下的固定相对路径；经过工作目录包含性检查，不接受命令行、环境变量、应用配置或客户端提供的目录，不接受绝对路径或 `..`。
- 外部程序直接使用参数数组执行，不经过 shell；环境变量采用明确允许列表。

### 17.2 后续部署与运维

Web 可执行文件如何安装、启动、守护、接入 systemd、设置文件所有者与权限以及开机启动，全部由运维人员处理，不是一期代码、测试或验收内容。Web 遇到文件访问错误时直接报告，不负责管理主机文件权限。

如需 HTTPS 或公网访问，运维人员可以在 Web 前增加 Caddy 或其他反向代理：

```text
浏览器
    │ HTTPS
    ▼
Caddy 或其他反向代理
    │ HTTP
    ▼
Web
```

该拓扑只是部署示例。域名、证书、TLS、HSTS、转发头信任、`Secure` Cookie、公网访问控制和安全审查均不属于一期。

## 18. 异常处理

| 异常 | 行为 |
|---|---|
| 表单或 JSON 无效 | 保存文本缓冲，保留最近有效对象，禁止应用 |
| 草稿修订冲突 | 返回 `409`，保留双方内容，不自动覆盖 |
| 引用或资源绑定错误 | 返回模块和字段路径，不停止核心 |
| 规则下载失败或超时 | 保留现有固定文件，记录错误，按周期再次尝试 |
| 新规则内容未变化 | 更新时间，不标记需要应用 |
| 新规则内容已变化 | 原子覆盖固定文件，引用档案标记需要应用 |
| 规则首次下载尚未成功 | 允许编辑，禁止相关档案应用 |
| sing-box 未安装 | 允许编辑与规则下载，提示管理员手动下载安装 |
| `sing-box check` 失败或超时 | 保留 `config.staging-<profile-id>` 中的本次候选与详细输出；不触碰正式 `config` 或核心进程 |
| 调用配置应用接口 | 先执行完整检查；检查失败不停止核心、不改变正式配置，成功后才进入可恢复的停止、切换和启动事务 |
| 子进程意外退出 | 状态改为失败，记录退出码，不伪造运行状态 |
| 核心下载或摘要校验失败 | 当前程序和运行进程保持不变 |
| 新核心更新后启动失败 | 恢复唯一备份程序并尝试重新启动 |
| 固定 `config` 外部漂移 | 阻止静默覆盖，要求管理员确认 |
| 浏览器断线 | 后端事务继续；恢复后重新读取真实状态 |
| 核心应用 JSON 损坏 | 不自动重置；按文件重要性拒绝写入或隔离档案 |

应用日志只记录操作类型、内部 ID、修订、摘要、阶段、耗时和结果，不记录完整配置或下载内容。

- 初始化密码、仅凭密码登录、退出和修改密码，页面与请求均不包含用户名。
- 只填写显示名称创建档案、自动保存、刷新恢复和多标签冲突，页面不提供配置目录输入。
- 创建规则资源、立即更新、定时状态和需要应用提示。
- 手动下载假核心并观察核心状态。
- JSON 编辑、错误跳转、最终模块预览和固定目录检查结果。
- 手动核心更新的确认、进度、成功和失败。
- 直接 HTTP 下的 Cookie、CSRF、安全响应头和 SPA 路由。

## 20. 一期验收标准

一期只有同时满足以下条件才完成：

- Web 的安装、systemd、Caddy、HTTPS 和公网部署不构成代码或验收依赖。
- 应用数据、正式配置、规则、日志和受管程序全部使用 Web 工作目录下的固定相对路径，不提供任何目录覆盖入口，也不依赖主机绝对路径。
- 未设置初始密码时拒绝进入管理服务；登录只使用密码，页面、API 和持久化数据均不存在用户名字段。
- 新档案由默认 Web 模板创建，Secret 和 `cache_id` 对每个档案唯一。
- 所有档案在 Web 数据目录保存独立草稿，并在 `config.staging-<profile-id>` 保留各自最新检查候选。
- 代理节点只通过出站模块 JSON 手工粘贴或编辑，并在草稿、预览和检查候选中无损保留。
- Web 规则资源配置与 sing-box 正式配置分离。
- 远程规则由 Web 下载到固定本地文件并按服务端周期更新，不建立规则版本历史。
- 原生远程 `route.rule_set` 不能直接应用或透传。
- 最终 `route.rule_set` 只引用本地文件，不包含资源 URL、`download_detour` 或更新周期。
- 规则内容变化后相关档案继续标记待处理；成功应用匹配的资源快照后清除，应用期间再次变化则保持待处理。
- “应用”先检查再停止核心；检查失败时正式配置与进程无副作用，成功时完成可恢复的目录切换、启动和状态提交。
- 同一时刻最多运行一个由 Web 管理的 sing-box 子进程，状态、PID、版本、当前档案和错误真实可见。
- sing-box 缺失时可由管理员手动下载；更新只在管理员确认后执行，并验证官方摘要和新程序可运行。
- 不维护固定 JSON Schema，检查结果以当前受管二进制 `sing-box check` 为准。
- 检查目录更新不会留下半写入候选；中断后恢复 `.previous` 或清理 `.preparing`，canonical 目录不被启动恢复删除。
- 草稿在浏览器刷新和 Web 重启后恢复，过期修订不会静默覆盖新修订。
- 配置编辑器、模块预览、检查错误和核心输出不对字段值做遮罩或脱敏。
- 本地 JSON 订阅在服务重启后恢复；页面和 API 不接受订阅 URL，也不执行网络拉取、解析、同步或定时刷新。
- 页面和 API 不提供合并配置下载、完整或脱敏配置复制及其他配置导出功能。
- 流量、连接、策略组、测速和高级运行控制明确不可用，不存在伪造结果。
- Go、Vue、集成、真实二进制契约和端到端测试全部通过。

## 21. 二期接口边界与演进路线

一期必须留下以下稳定契约：

- 档案具有稳定 ID、草稿修订、最近应用修订和综合摘要；唯一 `config` 当前对应哪个档案由 CoreManager 记录。
- 规则资源具有稳定 ID、固定本地文件、摘要、调度状态和引用关系。
- CoreManager 是唯一的 sing-box 子进程所有者；其他模块不能直接启动或终止核心。
- 当前档案、运行 PID、核心版本、应用修订和启动时间由 CoreManager 报告。
- ConfigGenerator 只在预览和检查过程中生成 sing-box 配置；应用流程后续另行设计。
- 前端高级运行页面只依赖独立 RuntimeApi 和 capabilities，不从档案草稿推断真实运行状态。

后续按独立规格拆分：

1. 二期 A：接入 Clash API 的只读状态、日志、流量、内存、连接和实时事件。
2. 二期 B：增加独立启动、停止、重启、异常自动恢复和更完整的核心状态机。
3. 二期 C：模式、策略组、测速、连接管理和实时日志控制。
4. 后续独立阶段：TUN、系统代理和系统 DNS。
