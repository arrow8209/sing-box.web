# config.json 自动化测试方案

> 状态：待审核

## 1. 目标

自动化测试以 Web 最终生成的 `config.json` 为唯一测试产物，验证它是否符合目标版本 sing-box 的官方配置规范。

本阶段遵循“先编写测试，再开发功能”的顺序。未通过自动化测试的配置不得进入真实 sing-box 人工测试。

## 2. 测试范围

自动化测试包含：

- 页面状态能否生成预期的 `config.json`。
- JSON 语法、顶层结构和字段类型是否正确。
- 必填字段、条件字段、默认值和字段省略是否符合官方文档。
- 标签、出站、DNS 服务器、规则集和其他跨模块引用是否有效。
- 不同版本中新增、弃用或移除的字段是否被正确处理。
- 导入、编辑、保存和再次导出后，配置语义是否保持一致。
- 自定义 JSON 中受支持但 Web 尚未结构化编辑的字段是否无损保留。
- Web 内部使用的 `id`、界面状态和临时字段是否不会写入 `config.json`。

自动化测试不包含：

- 启动、停止或重启 sing-box。
- 创建 TUN 网卡或修改路由。
- 修改宿主机系统代理、DNS、防火墙或网络接口。
- 验证代理节点是否真正可连接。
- 验证实时流量、连接、日志和内存数据。

以上内容属于[真实 sing-box 人工协作测试方案](./manual-testing.md)。

## 3. 权威依据与版本管理

配置规则只采用以下官方依据：

1. 目标版本对应的 sing-box 官方配置文档。
2. sing-box 官方提供的 JSON Schema。
3. 目标版本核心的 `sing-box check` 校验结果。

`../demo/GUI.for.SingBox` 只能作为界面功能和操作流程参考，不能作为配置字段标准。

开始实现测试前必须明确目标 sing-box 版本。测试用例需要记录：

- 目标版本。
- 对应的官方文档 URL。
- 涉及字段的引入、弃用或移除版本。
- 官方文档或 Schema 的获取日期。

如果官方文档、Schema 和目标版本核心出现不一致，测试应停止并记录差异，不得静默放宽规则或自行猜测兼容行为。

## 4. 安全边界

自动化阶段允许调用的 sing-box 命令仅限：

```text
sing-box version
sing-box check -c <临时配置文件>
```

不得调用 `sing-box run`，也不得通过 service、systemd、Docker 或其他方式启动核心。

执行 `sing-box check` 时应满足：

- 使用固定版本的 sing-box 二进制文件。
- 配置和关联测试资源位于临时测试目录。
- 本地规则集、证书等关联文件使用测试夹具，不读取生产文件。
- 在环境支持时禁用该检查进程的网络访问。
- 设置明确超时，超时后测试失败。
- 不使用真实订阅凭据、节点密码、证书私钥或 API Secret。

## 5. 测试驱动开发流程

每个配置功能按以下顺序开发：

1. 确认目标字段的官方文档和适用版本。
2. 定义页面输入、预期输出和禁止出现的字段。
3. 先编写失败的自动化测试。
4. 实现最小配置生成逻辑，使测试通过。
5. 增加边界值、错误输入、字段组合和引用关系测试。
6. 使用官方 Schema 和 `sing-box check` 复核完整配置。
7. 运行全部配置回归测试，确认没有破坏其他模块。
8. 通过后才允许进入下一项开发。

修改已有功能同样必须先补充能够复现问题的失败测试。

## 6. 校验层次

### 6.1 生成结果校验

- 相同输入生成稳定、可预测的配置。
- 必要字段存在，未启用的可选模块被正确省略。
- 数字、布尔值、数组、对象和字符串不会被错误互转。
- 空值处理符合官方要求，不输出无效的 `null`、空字符串或空容器。

### 6.2 JSON Schema 校验

- 使用目标版本对应的官方 Schema。
- 校验字段类型、枚举、对象结构和未知字段。
- Schema 文件应固定版本或摘要，避免远程内容变化导致结果漂移。

### 6.3 业务语义校验

Schema 不能覆盖的关系由项目测试补充：

- tag 在规定作用域内唯一。
- route、DNS、detour、规则集和策略组引用的 tag 必须存在。
- Selector、URLTest 等策略组至少包含一个有效成员。
- 端口范围、网络前缀、时间单位和地址族组合合法。
- 条件字段只在对应类型或开关启用时出现。
- 已禁用项目不会被活动配置引用。

### 6.4 官方核心检查

每个代表性完整配置都应通过目标版本的：

```text
sing-box check -c config.json
```

检查失败时保存退出码和标准错误输出，但不得继续尝试启动核心。

### 6.5 往返一致性校验

对支持导入的配置执行：

```text
config.json → Web 数据模型 → config.json
```

除字段排序和已明确记录的默认值归一化外，两次配置应保持语义一致。

## 7. 顶层模块覆盖矩阵

| 模块 | 主要自动化测试内容 |
|---|---|
| `$schema` | 字符串格式、保留和省略策略 |
| `log` | 等级、输出、时间戳及禁用状态 |
| `dns` | 服务器、规则、缓存、FakeIP 和跨模块引用 |
| `ntp` | 启用条件、服务器、端口、间隔和 detour |
| `certificate` | 系统证书、自定义证书和文件引用 |
| `certificate_providers` | 类型专属字段、tag 和证书提供器列表 |
| `http_clients` | tag、TLS、代理出站和复用配置 |
| `network_namespaces` | tag、类型及平台/版本限制 |
| `endpoints` | WireGuard、Tailscale、OpenVPN、OpenConnect 等类型专属字段 |
| `inbounds` | 所有入站类型、监听、用户、TLS、嗅探及 TUN 配置 |
| `outbounds` | 所有出站类型、认证、TLS、传输、detour 和策略组成员 |
| `route` | 默认行为、规则、动作、规则集、接口和 DNS 引用 |
| `services` | 各服务类型、监听参数和类型专属字段 |
| `experimental` | Clash API、缓存文件及其他版本限定功能 |

每增加一种具体类型，至少应提供：

- 最小有效配置。
- 完整有效配置。
- 缺少必填字段的无效配置。
- 字段类型错误的无效配置。
- 边界值配置。
- 与其他模块组合后的完整配置。

## 8. 测试用例规范

自动化测试编号建议使用：

```text
CFG-<模块>-<序号>
```

示例：`CFG-INBOUND-001`、`CFG-ROUTE-014`。

每个用例至少记录：

```text
编号：
目标版本：
官方文档：
测试目的：
页面输入：
预期 config.json：
禁止出现的字段：
预期 Schema 结果：
预期 sing-box check 结果：
```

无效用例还必须声明预期错误位置和用户可理解的错误信息，避免只判断“发生错误”。

## 9. 建议目录结构

实际落地前仍需单独审核，建议结构如下：

```text
tests/
└── config/
    ├── fixtures/
    │   ├── inputs/
    │   ├── expected/
    │   └── resources/
    ├── modules/
    ├── references/
    └── helpers/
```

- `inputs` 保存页面数据模型输入。
- `expected` 保存预期的完整或局部配置。
- `resources` 保存测试证书、规则集等无敏感信息的夹具。
- `references` 记录目标版本和官方文档链接。
- `helpers` 提供 Schema、引用关系和 `sing-box check` 调用封装。

## 10. 通过标准

配置功能只有同时满足以下条件才算完成：

- 新增测试先失败，功能实现后通过。
- 所有相关模块测试通过。
- 完整配置通过目标版本官方 Schema。
- 代表性配置通过 `sing-box check`。
- 全量配置回归测试通过。
- 测试用例包含官方文档和目标版本依据。
- 没有执行任何会启动核心或改变网络状态的操作。
